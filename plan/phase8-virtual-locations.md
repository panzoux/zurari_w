# Phase 8 — 仮想ロケーション基盤

**状態**: `[ ]` 未着手(ガワのみ。着手時にこのファイルへタスクを書き下す)

## 目的

「列が指す場所」を実ファイルシステムのパス文字列から抽象化し、アーカイブ内・検索結果・
シェル名前空間などを列として開けるようにする。**それ自体はユーザーに見える機能を増やさない
純粋なリファクタ**であり、Phase 9(アーカイブ)の土台になる。

## 現状

`Column.Path` は `string` で、`""` = ドライブ一覧 という特別扱いが1箇所だけ存在する。
これ以上の仮想的な場所を増やすと、`""` のような特別扱いが各所に散らばって破綻する。

## スコープ

### やること

- [ ] `Location` 型の導入(案):

      Location = RealDirectory(path)
               | Drives
               | Archive(archivePath, innerPath)   ← Phase 9 で使う
               | SearchResult(query, roots)        ← 将来

- [ ] `Column.Path`(string)を `Column.Location` へ移行
- [ ] `Effect.ReadDirectory` を Location ベースに変更
- [ ] パス表示・タイトル生成(`StateProjection`)の対応
- [ ] `DirectoryWatcher` の対応 — **仮想ロケーションは監視できない**ので、監視対象は
      `RealDirectory` のみに絞る(現状は全列のパスを渡している)
- [ ] ジョブ(コピー/移動/削除)の対応 — 仮想 → 実への変換が必要な操作を洗い出す
- [ ] 既存の全テスト(Core 193本を含む)の移行

### やらないこと

- 新しい仮想ロケーションの実装そのもの(アーカイブは Phase 9、検索結果はさらに後)。
  本フェーズは **`RealDirectory` と `Drives` の2つだけを Location で表現し直す**ところまで。
  つまり外から見た振る舞いは一切変わらないのが正しい完了状態。

## 設計メモ

- 移行は機械的だが範囲が広い。テストが多い(全体 471本)ので、コンパイルエラーを潰していけば
  抜けは検出できる。TDD というより「型を変えて全部直す」タイプの作業。
- `Location` を record union(既存の `Msg` / `Effect` と同じ書き方)にすれば、Core の純粋性を
  保ったまま表現できる。
- Phase 7 の `Pane` 導入(`AppState` の構造変更)と本フェーズは**どちらも Core 全体に触る**。
  着手時に、まとめて実施した方が総コストが安くないか再検討する。
